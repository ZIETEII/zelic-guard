# ZELIC Guard — OpenAI Build Week Engineering Brief

## Mission

Build **ZELIC Guard — Intent Contracts for AI Agents**, a complete, judge-testable Developer Tools submission for OpenAI Build Week 2026.

Tagline: **AI agents can plan freely. They can act only inside an approved contract.**

The product turns a risky agent action into a typed, human-approved contract, then evaluates execution attempts with a deterministic policy engine. Matching actions are allowed; scope drift, recipient drift, cost overruns, expired contracts, max-run violations, and replay attempts are blocked with human-readable evidence.

## Product experience

The first screen must be a usable application, not a generic landing page.

Use a premium mission-control aesthetic without purple gradients or generic AI imagery. Suggested visual direction:

- near-black graphite background;
- warm ivory text;
- acid signal green for allowed decisions;
- amber for pending approval;
- signal red for denied decisions;
- technical grid/noise treatment, restrained motion, strong typography;
- responsive desktop three-stage flow and stacked mobile layout;
- accessible contrast, focus states, keyboard operation, and reduced-motion support.

Primary three-stage flow:

1. **Intent** — a natural-language request such as “Send invoice INV-2048 to finance@northstar.test once, for no more than $0.25, before 18:00.”
2. **Contract** — structured action, channel, target, allowed recipients, resource fingerprint, max cost, max runs, expiration, status, and contract fingerprint. The human can review/edit constraints and approve.
3. **Execution Gate** — run a valid attempt or adversarial simulations and inspect every rule decision in an audit timeline.

Required scenario controls:

- Valid execution → allowed.
- Recipient drift → blocked.
- Cost overrun → blocked.
- Replay using a consumed execution ID → blocked.
- Expired contract → blocked.
- Reset lab → clean initial state.

Required visible evidence:

- contract status and fingerprint;
- verdict: ALLOW or DENY;
- per-rule checks with pass/fail and reason codes;
- audit timeline with deterministic timestamps/order;
- counters for allowed and blocked attempts;
- machine-readable contract JSON view;
- clear “simulation only — no email/payment is sent” disclosure.

Include loading, initial/empty, error, proposed, approved, allowed, denied, expired, and reset states.

## Core architecture

Use the generated Next.js 16 App Router project with TypeScript, React 19, Tailwind CSS 4, and Vercel deployment.

Do not add a database or authentication for this public demo. Do not use Clerk, Supabase, Firebase, Auth0, Redis, or unrelated services.

Implement a framework-independent domain layer under `src/lib/guard/`:

- Zod schemas and inferred TypeScript types for contracts, constraints, execution attempts, rule checks, verdicts, and audit events.
- Stable canonical serialization and SHA-256 fingerprinting.
- Pure deterministic `evaluateExecution` behavior.
- Explicit machine-readable reason codes.
- Dependency-injected replay/history state rather than hidden global behavior in the pure engine.
- Seed fixtures for the invoice scenario and adversarial variants.

Suggested reason codes:

- `CONTRACT_NOT_APPROVED`
- `CONTRACT_EXPIRED`
- `ACTION_MISMATCH`
- `CHANNEL_MISMATCH`
- `TARGET_MISMATCH`
- `RECIPIENT_NOT_ALLOWED`
- `RESOURCE_FINGERPRINT_MISMATCH`
- `COST_LIMIT_EXCEEDED`
- `MAX_RUNS_EXCEEDED`
- `REPLAY_DETECTED`
- `ALL_RULES_PASSED`

Add server route handlers for compile/approve/evaluate only when they improve the architecture. Sensitive policy evaluation must not exist solely as decorative frontend logic. A demo in-memory replay adapter is acceptable if its limitation and production adapter interface are documented.

## TDD mandate

Follow strict vertical RED → GREEN → REFACTOR cycles for every new domain behavior.

For each slice:

1. Write one failing test.
2. Run it and verify the expected failure is caused by missing behavior.
3. Implement only enough to pass.
4. Run the focused test and full suite.
5. Refactor while green.
6. Commit frequently.

Use Vitest for unit/integration tests. Add Playwright only if it can run reliably in the time budget; otherwise provide a deterministic smoke script plus browser verification.

Minimum test matrix:

- valid approved execution is allowed;
- proposed/rejected/expired contracts are denied;
- action/channel/target mismatch denied;
- recipient drift denied;
- resource fingerprint drift denied;
- cost overrun denied;
- max runs denied;
- reused execution ID denied;
- malformed contract/attempt rejected by Zod;
- canonical fingerprint stable across object key order;
- core UI flow can approve, allow one run, and block an attack.
